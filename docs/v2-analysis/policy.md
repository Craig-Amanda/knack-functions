# Shared context for knackFunctions V2 analysis agents

## Repository facts (verified in this session)
- Repo: /home/user/knack-functions. Source of truth: `knackFunctions.js` (23,034 lines, 310 functions, 9 classes, ~400 globals).
- Loaded by Knack apps as a classic `<script>` (not a module) from jsDelivr: `dist/knackFunctions.global.min.js`, pinned by tag (see assetLoader.js). Consumers: GAP-Track, Spot (and others: "Powderpigs Brain" defines a local copy of one helper).
- Because it is a classic script, EVERY top-level `function`, `class`, `const`, `let` is a page global. `eslint/generate-globals.mjs` parses the file with acorn (`sourceType: 'script'`) and emits `eslint/knack-functions-globals.json`; consuming apps lint against it. Therefore every existing global name is public API and must keep existing in V2 (either as the real implementation or as a shim).
- Two classic scripts cannot both declare the same top-level `const`/`class`/`let` (SyntaxError), so V2 is a full standalone replacement file, built up progressively, not an overlay loaded after V1.
- Repo conventions: 4-space indent, single quotes, JSDoc on functions, mostly UK spelling (normalise, capitalise, colour) but inconsistent (normalize*, Summarize). Error reporting via `errorHandler.handle(error, additionalInfo, errorSource)` with a console fallback defined at the top of the file. Constants `CLASS_HIDDEN='ktlHidden'`, `CLASS_DISPLAY_NONE='ktlDisplayNone'` come from KTL.
- External runtime globals used by the file (not defined in it): `$`/`jQuery` (58 functions), `Knack` (24), `ktl` (Knack Toolkit Library, 22), `ktlKeywords`, `React`/`ReactDOM`/Quill (rich text), `FIELD_IDS_FOR_LOGGED_IN_USER`, `SET_CURRENT_DATE_FIELDS`, `WEEK_NUM_SHARED_AREA_GRID`, `CONNECTION_FIELDS_OBJECT`, `KN_ASSET_PREFIX`, `assetURLs`, `isDeveloper`, `registrationHandler`, `formatDatePicker` (app-supplied).
- Git history only goes back to June 2026 (repo was re-created), so age must be inferred from style: jQuery-first code, missing JSDoc, `var`, callback-style, `//knack` trailing comments, `};` after function declarations, `keyCode`, `$.expr[':']` extensions are the ~5-year-old layer. The bulk-actions, KnackAPI, KnackNavigator, KnackValueResolver, KnackError, version-refresh, file-carousel, grid-truncation, interactive-table code is recent (2026) and already modern.
- Existing test: `tests/truncateColumnsInGrid.test.cjs` (node:test + Playwright, slices the helper out of the source by string markers). Chromium is preinstalled at /opt/pw-browsers; network to CDNs is blocked in this environment.

## Knack platform facts (from the Knack developer docs, docs.knack.com - NOT reachable from this sandbox, so these are from prior knowledge; mark anything you rely on as "unverified against live docs" if unsure)
- Custom JavaScript runs as one classic script in the page. Globals available: `Knack`, `$`/`jQuery` (Knack bundles jQuery; version is Knack's choice - do not depend on plugin-specific or version-specific jQuery behaviour), `LazyLoad` (for loading external libraries), Backbone/Underscore internals.
- Knack is a single-page app with hash routing (`#scene-slug/record-id/`). Scenes and views re-render on navigation, filtering, sorting, paging and inline edits. DOM references go stale; rebind on render events, never cache elements across renders.
- Render/lifecycle events are jQuery events on `document`:
  - `knack-scene-render.scene_x` / `knack-scene-render.any` -> (event, scene)
  - `knack-view-render.view_x` / `.any` / by type e.g. `.form`, `.table`, `.details` -> (event, view, data)
  - `knack-records-render.view_x` -> (event, view, records)
  - `knack-record-create.view_x`, `knack-record-update.view_x` -> (event, view, record)
  - `knack-record-delete.view_x` -> (event, view, recordId)
  - `knack-form-submit.view_x` -> (event, view, record)
  - `knack-cell-update.view_x` -> (event, view, record)  (inline edit)
  - `knack-page-render.any` -> (event, page)
- Knack object API commonly used: `Knack.views[viewKey]` (Backbone view: `.model`, `.model.data` collection for grids, `.render()`), `Knack.models[viewKey]`, `Knack.scenes`, `Knack.objects`, `Knack.fields`, `Knack.router.navigate(hash, {trigger:true})` / `Knack.router.current_scene_key`, `Knack.hash_id`, `Knack.getUserAttributes()` -> {id, name, email, values, roles}, `Knack.getUserRoles()`, `Knack.getUserRoleNames()`, `Knack.getUserToken()`, `Knack.showSpinner()` / `Knack.hideSpinner()`, `Knack.closeModal()`, `Knack.application_id`, `Knack.app` (app model), `Knack.session`.
- DOM conventions: view root `#view_x.kn-view`; form inputs `#kn-input-field_x` wrapper and `#view_x-field_x` input ids; table cells `td.field_x`, rows `tr[id=<recordId>]`; details `.kn-detail.field_x .kn-detail-body`; list items `.kn-list-item-container`; modals `.kn-modal` / `.kn-modal-bg`; submit `.kn-submit button`; messages `.kn-message`; spinner `.kn-spinner`. Connection dropdowns use the Chosen plugin (`.chzn-container`, trigger `chosen:updated` after changing options); date fields use jQuery UI datepicker + a timepicker plugin (`.ui-timepicker-input`).
- View-based REST API (safe from the browser): `https://api.knack.com/v1/pages/{scene_key}/views/{view_key}/records` with headers `X-Knack-Application-Id`, `X-Knack-REST-API-Key: knack`, `Authorization: <Knack.getUserToken()>`. Query: `page`, `rows_per_page` (max 1000), `filters` (URL-encoded JSON `{match, rules:[{field, operator, value}]}`), `sort_field` + `sort_order` (NOT `sort[0][field]`). Responses `{total_pages, current_page, total_records, records}`. Object-based API needs the secret API key and must never be used in the browser. Rate limits: ~10 requests/second and a daily plan limit; 429 when exceeded. Record payloads expose `field_x` (HTML display) and `field_x_raw` (raw; connections `[{id, identifier}]`, date_time `{date, date_formatted, hours, minutes, am_pm, unix_timestamp, iso_timestamp, timestamp, time}`).

## Modern JavaScript targets for V2 (ES2020+; Knack apps run in evergreen browsers)
- `const`/`let` only; arrow functions for callbacks; default parameters; destructuring; optional chaining `?.`; nullish coalescing `??`; template literals; spread; `Array.from`, `.flatMap`, `.at()`, `Object.entries/fromEntries`, `Object.hasOwn`; `structuredClone`; `Intl.DateTimeFormat('en-GB')` / `Intl.NumberFormat('en-GB', {style:'currency', currency:'GBP'})`; `AbortController` for fetch timeouts; `async`/`await` over callback chains; `MutationObserver` over `setTimeout` polling; `WeakMap` for per-element state; `CSS.escape`; `element.closest/matches/querySelector(All)`, `classList`, `dataset`, `hidden`, `insertAdjacentHTML/Element`, `replaceChildren`, `textContent` over `innerHTML` for text; `requestAnimationFrame` for layout-dependent work; idempotent `ensure*` functions (inject a style once by id).
- jQuery policy (explicit rule from the repo owner): V2 implementation code uses NO jQuery. Exactly three exceptions, where Knack leaves no native route: (1) Knack lifecycle events (`knack-view-render`, `knack-scene-render`, `knack-records-render`, ...) must be bound with `$(document).on(...)` because Knack triggers them through jQuery's `trigger` (use the `onKnackEvent` primitive); (2) Knack's Chosen select plugin on connection/multiple-choice dropdowns (`$(select).trigger('chosen:updated')`, `.chosen(...)`); (3) Knack's jQuery UI date picker and time picker widgets (`$(input).datepicker(...)`, `.timepicker(...)`). Every other jQuery call in V1 is replaced with native DOM.
- Return types under that rule: where V1 returned a jQuery collection, the V2 implementation returns native `Element` / `Element[]` and ships under a NEW descriptive name (UK spelling, plural when it returns an array). That is a return-type change, so the OLD name becomes a compatibility shim that wraps the native result with `toJQuery()` for existing callers. Shims and the `:textEquals` pseudo-selector shim are the only other places jQuery may appear, and they are deleted in V3. Accepting a jQuery object as an INPUT (via `resolveElement`/`resolveElements`) is fine and is not "using jQuery".
- New code MUST still accept the same inputs the old function accepted (selector string, Element, NodeList, jQuery object, array).
- Succinct: no commented-out code, no duplicate branches, no defensive checks for impossible states, one responsibility per function, early returns, no `//knack` tag comments, no dangling `};`.
- Errors: throw/return consistently; report via `errorHandler.handle(err, {context}, 'functionName')`; never swallow silently.
- Keep JSDoc (types + @param + @returns), add `@deprecated Use X` on shims. Use UK spelling for NEW identifiers; never rename an existing global (aliases via shim only).

## Signature-compatibility and shim policy (binding for every verdict)
- "Signature" means: global name, parameter list and order, accepted input types, return type, sync/async nature, thrown errors, and DOM side effects that CSS or other code rely on (class names, ids, data attributes, custom events).
- If V2 changes any of those, the old name must remain as a SHIM: same old signature, maps old arguments to the new implementation, returns the old type, documented `@deprecated`. Shims are grouped in one "Compatibility shims" section at the end of V2 so V3 can delete them.
- Prefer keeping the signature and modernising the body. Only change a signature when it materially simplifies callers (e.g. 5+ positional params -> options object) or removes a jQuery-only type.
- Dedupe: pick ONE canonical implementation; the others become shims that call it. Known or suspected duplicates/overlaps to check: escapeHTML vs escapeHtml; getTableRows vs getAllTableRows; getValueFromDetail vs getValueFromDetailBody vs waitGetValueFromDetail; resolveElement vs normaliseToElement vs bulkActionResolveElement vs resolveElements vs normaliseInputs; getElementByText vs findElementByText (+ `$.expr[':'].textEquals`); setVisibility vs showIf vs toggleVisibility vs toggleElements vs toggleMessage; showHideViewContent vs toggleShowHideViewContent vs showHideViewGroupContent vs shrinkContent; getCheckedRowIds vs getCheckedRows; isNodeList/isjQueryInstance; removeHtml vs removeHtmlWithFormatting; weeksBetween/convertToDateObj/parseDateObject; getRecordID vs getIdFromElement vs getConnectionIdFromHtml; getViewRootElement vs bulkActionFindViewRoot vs getViewMountElement; cssEscape vs CSS.escape; debounce vs API_TIMER; bulkActionIsPlainObject/objectOrEmpty vs generic.
- Dead code: `$(document).keydown` F2 `debugger` hook, `evaluate(a)` sandbox helper, `API_TIMER` (unused in file), `getMax` are candidates for `remove-dead` / `deprecate` (keep the global as a no-op or thin shim, log a deprecation).

## Wave assignment rules
- Wave 1 (rewrite now in knackFunctionsV2.js): old-style code, roughly <= 150 lines, no third-party library coupling (Quill/React/jQuery-UI widgets), risk low or medium, and a clear gain (jQuery removal, dedupe, dead branches, async/await). Also all foundation primitives other functions will use.
- Wave 2: medium modules that are modern-ish or widget-coupled (pickers, grid truncation, show/hide groups, menu buttons, file carousel, interactive table, quick toggles): port with targeted improvements once wave 1 is stable.
- Wave 3: large recent classes (KnackAPI, KnackNavigator, KnackValueResolver, KnackError, bulk actions, MultiFormSubmissionCoordinator, version refresh controller): port as-is with dead-code removal and consistency fixes only; no signature changes.
